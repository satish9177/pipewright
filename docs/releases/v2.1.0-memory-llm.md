# v2.1.0 — Memory M1 + LLM Provider Foundation

## Release Summary

This release completes two foundational milestones: project-scoped memory
(Memory M1) and the multi-provider LLM backend abstraction (LLM-M1/M2).

The pipeline roles (triage, planner, coder) no longer import provider SDKs
directly. All LLM calls pass through `backend.llm`, which resolves the active
provider and model from environment variables at startup. Gemini remains the
default; Anthropic, OpenAI, and DeepSeek are ready for use.

Deployment is intentionally paused for local validation. Ollama is intentionally
deferred to a later phase or indefinitely.

No DB schema changes were introduced by this release.

---

## Memory M1 Highlights

### What Was Delivered

- **Project-scoped memory** — memory entries belong to a project and are never
  shared across projects. There is no global memory fallback.
- **Memory validation** — backend rejects entries that contain secrets, PII
  patterns, or prompt injection syntax before saving.
- **Prompt builder** — `MemoryPromptBuilder` assembles active project memory
  into a structured block injected into triage, planner, and coder prompts.
- **Backend Memory API** — CRUD endpoints for memory entries: create, list,
  update (content/status), archive. `GET /projects/{id}/memory` returns only
  active entries.
- **Frontend Memory panel** — project settings tab with entry list, add/edit
  form, archive action, and status badges.
- **Bootstrap suggestions** — backend generates candidate memory entries from
  the project repo (README, package files, language/framework signals). Returned
  as a suggestions list; nothing is saved until the user approves.
- **Suggestion approve/reject UI** — each suggestion can be approved (saved as
  active entry) or dismissed individually.
- **Nested manifest discovery** — bootstrap discovery walks the repo tree and
  finds package manifests in nested directories, not only the root.
- **Prompt preview** — archived entries are excluded from injection; the preview
  reflects only active entries.
- **Memory docs and smoke checklist** — `docs/memory/m1-memory-user-flow.md`
  and `docs/memory/m1-memory-smoke-test.md`.

## LLM Provider Highlights

### What Was Delivered

- **`backend.llm` abstraction** — a public API (`complete_for_role`,
  `get_provider_for_role`, `log_token_usage`, `validate_all_roles`) that
  pipeline roles call instead of importing provider SDKs.
- **`LLMRequest` / `LLMResponse` envelope** — structured request/response types
  with `messages[]`, `model`, `temperature`, `max_output_tokens`,
  `timeout_seconds`, `response_format`, and `extras`. Roles read only
  `response.text`.
- **Async provider interface** — `BaseLLMProvider` with `name`,
  `supports_model`, and `complete(request)`.
- **GeminiProvider** — `google.generativeai` SDK isolated to
  `backend/llm/providers/gemini.py`.
- **AnthropicProvider** — `anthropic` SDK isolated to
  `backend/llm/providers/anthropic.py`. System messages are concatenated and
  passed as Anthropic's `system=` parameter.
- **OpenAIProvider** — `openai` SDK isolated to
  `backend/llm/providers/openai.py`. Accepts `gpt-*` and `o`-series models.
- **DeepSeekProvider** — uses the `openai` SDK with
  `base_url="https://api.deepseek.com"` (OpenAI-compatible API). Isolated to
  `backend/llm/providers/deepseek.py`. Accepts `deepseek-*` model names.
- **FakeProvider** — deterministic stub for tests and local dev. Returns
  `request.extras.get("response_text", "fake response")`. Must not be used in
  production pipelines without valid JSON fixtures.
- **Provider isolation guards** — static source-scan tests in
  `backend/tests/test_guards_provider_isolation.py` assert each SDK import
  exists only in its designated adapter file.
- **Role env config** — provider and model resolved per role via
  `<ROLE>_LLM_PROVIDER` / `<ROLE>_LLM_MODEL`, falling back to
  `DEFAULT_LLM_PROVIDER` / `DEFAULT_LLM_MODEL`, then hardcoded Gemini.
- **Structured `[LLM]` log line** — `log_token_usage` emits
  `[LLM] role=... provider=... model=... input_tokens=... output_tokens=... finish_reason=... run_id=...`
  after every `complete_for_role` call. No prompt content, response text, or
  API keys appear in logs.
- **Docs** — `docs/llm/provider-matrix.md`, `docs/llm/m1-provider-abstraction.md`,
  `docs/llm/m2-provider-smoke-checklist.md`, and per-provider reference docs.

## Env Config Summary

### Role/Model Selection

| Variable | Scope |
|----------|-------|
| `DEFAULT_LLM_PROVIDER` / `DEFAULT_LLM_MODEL` | All roles (fallback) |
| `TRIAGE_LLM_PROVIDER` / `TRIAGE_LLM_MODEL` | Triage role only |
| `PLANNER_LLM_PROVIDER` / `PLANNER_LLM_MODEL` | Planner role only |
| `CODER_LLM_PROVIDER` / `CODER_LLM_MODEL` | Coder role only |
| `REVIEWER_LLM_PROVIDER` / `REVIEWER_LLM_MODEL` | Reviewer role only |
| `SUMMARY_LLM_PROVIDER` / `SUMMARY_LLM_MODEL` | Summary role only |

Precedence: explicit overrides dict → role-specific env → default env →
hardcoded Gemini fallback.

### API Keys

| Variable | Required |
|----------|----------|
| `GEMINI_API_KEY` | Yes (startup) |
| `ANTHROPIC_API_KEY` | No (validated on first use) |
| `OPENAI_API_KEY` | No (validated on first use) |
| `DEEPSEEK_API_KEY` | No (validated on first use) |

See `docs/llm/provider-matrix.md` for full configuration examples and
`docs/ops/pre-deployment-checklist.md` for startup requirements.

## Known Limitations

- **No provider settings UI** — provider and model are env-only; no project
  settings page for LLM config.
- **No DB-stored provider API keys** — keys are not persisted in the database.
- **No encrypted BYOK provider secrets** — provider keys are plain env vars;
  no per-project encrypted key storage for end users.
- **No fallback chains** — if the selected provider fails, the error propagates
  normally; there is no automatic retry to a different provider.
- **No auto-routing** — provider selection is always explicit via env; no
  routing based on cost, capability, or prompt characteristics.
- **No execution modes** — no streaming, batching, or parallel calls.
- **No tool/function calling** — structured tool use is not implemented.
- **No Ollama** — local provider support is deferred indefinitely.
- **Deployment paused** — deployment work is intentionally paused pending local
  validation.
- **No `llm_calls` audit table** — per-run provider/model audit persistence is
  deferred; only the structured `[LLM]` log line is available.
- **SQLite / single-instance** — project execution locks, event bus, and live
  log buffer are all in-process. Multi-instance deployment requires a
  distributed lock and durable event bus.

## Next Possible Phases

- **Local stabilization / bug fixes** — run the full local stabilization
  checklist, fix any regressions before moving forward.
- **BYOK / provider secret design** — design encrypted per-project API key
  storage so end users can supply their own provider keys.
- **Provider/model UI** — project settings page for selecting provider and
  model per role without env vars.
- **Reviewer and summary roles** — migrate remaining pipeline roles to
  `backend.llm`; they are config-ready but not yet implemented.
- **Deployment** — Cloud Run / GCP deployment after local validation is
  complete; requires distributed lock, durable event bus, and Redis or DB-backed
  state.
- **Ollama** — local provider support; deferred or possibly never, pending
  demand and design.
