## 0. The headline invariant (read before anything else)

§5.4 is **DECIDED** (2026-06-12): a delivered high-severity reviewer finding makes the human's **Approve** require an explicit acknowledgement first. This gives the reviewer **procedural** weight (the human must *look*), never **decisional** weight. The reviewer keeps zero authority — it cannot reject, approve, commit, push, merge, or block forever — exactly as `reviewer_models.py:10-24` already guarantees ("Nothing here grants approval authority… cannot weaken #26/#27/#28").

**The single non-negotiable invariant of this slice — the reviewer must NEVER become a denial-of-approval vector:**

> A review that is **missing, `unavailable`, `failed`, still pending, stale (bound to an old diff hash), or carries no *current* `high` × {`requirement_mismatch`, `security`} finding** imposes **no gate at all** — Approve stays enabled. When the gate *does* fire (a delivered current high finding exists), it is **always satisfiable by the human**: acknowledge → proceed. The AI can never stop a human who chooses to proceed.

This is the structural guarantee from §4.5 ("the ack requirement attaches only to *delivered* high-severity findings, mirroring how #28F treats a NULL verdict — no ack required"). **Two SEPARATE code paths must each fail open, and the design must prove both:**

- **Display** — the read overlay is already fail-closed (`chunk_review_read_model.load_chunk_review_read_model:138` returns `None` on any error → "no review"), so a read-path display failure degrades to "no findings → no gate."
- **Enforcement (the path that actually gates Approve)** — the route-level review-ack precondition does **not** read through the display overlay; it is a separate path. It MUST wrap its own edge I/O (`current_chunk_review_identity` / `get_review_by_checkpoint_hash` / `get_latest_review`) so that **any exception, or any indeterminate review lookup or diff identity, yields an empty gating set → no gate → Approve stays enabled.** The pure gating selector's default/error branch is "no findings"; only a successfully-loaded, *current*, `high`×A1 finding is ever "blocked." Display fail-closed is **necessary but not sufficient** — proving the overlay fails open does NOT prove the precondition does, because they are different paths.

**If you cannot prove with a test — at BOTH the chunk gate and the final gate — that (i) a down/absent/stale reviewer and (ii) a raising enforcement selector each leave Approve working, stop and escalate — do not ship.** The second proof that must exist: a delivered high finding → ack required → human acks → Approve proceeds (the gate is soft, never terminal).

This is the mirror image of item 14's §0 (which protected a *good chunk* from a failed refinement). Item 15's §0 protects the *human's ability to approve* from an advisory AI.

### Decisions already made (do not re-litigate — from the §5.4 ruling)

- **A1 — the ack-required set: `high` × {`requirement_mismatch`, `security`} only.** A finding gates iff `severity == high` **and** `category ∈ {requirement_mismatch, security}`. `warning`/`info` **never** gate. All other `high` categories (`correctness`, `test_gap`, `scope`, `maintainability`, `uncertainty`) are a **future per-project policy opt-in, default OFF** — ship the default constant set and a clean named seam, **do not build per-project overrides now** (`policy.py:11-14` explicitly defers layered/per-project config to a later phase; respect that).
- **A2 — attach point: the chunk approval gate AND the final approval gate.** This is a deliberate **expansion** of #28F, which today is **final-only and explicitly does not gate chunk approval** (`test_validation_ack_store.py:18-19`). Kept **soft** (ack, never block). Both attach as **route-level preconditions** (the #28F shape), leaving the safety-critical gate machinery (`approval_gate.py`) and the orchestrator commit path untouched.
- **A3 — diff-hash-bound acknowledgement + staleness, reuse #28F exactly.** A reviewer-finding ack binds to the chunk's current diff identity — the *same* `compute_chunk_diff_hash` (`test_validation_ack_store.py:126`) that #28F and review staleness already share, so reviewer-ack staleness and review staleness cannot diverge. A retry/steer/refinement moves the hash → a new review runs bound to the new hash → any prior ack (old hash) is **stale** → re-ack required. **Panel-level ack** (one ack per (run, chunk, current diff hash) covers that diff's whole findings panel), mirroring #28F's one-ack-per-(chunk, verdict, hash). Per-finding granularity is a noted future option, not this slice.
- **A4 — "steer this" reuses the existing steer surface; NO new steering backend semantics.** A gating finding offers one click that converts it into a steer turn through the **existing** `POST /runs/{run_id}/chunks/{n}/steer` route and the existing `steer_chunk` dispatcher (`chunked_orchestrator.steer_chunk`) — which already routes a `failed` chunk to item 13 and a `completed` chunk to item 14. **"Steer this" is offered ONLY where that dispatcher can act: the failed-chunk surface (`failed` → item 13) and the completed / final-gate surface (`completed` → item 14). It is NOT offered at the chunk-approval gate, where the chunk status is `awaiting_chunk_approval` — a status `steer_chunk` does not handle (it returns a side-effect-free 422 for any status other than `failed`/`completed`, `chunked_orchestrator.py:3719-3736`). Making it work there would require a new `awaiting_chunk_approval` dispatch branch, which A4 forbids.** At the chunk-approval gate a gating finding's only affordances are **acknowledge** (clear the soft gate) and the existing **reject** — not steer. The only permissible backend addition is a **pure, deterministic finding→steer-text formatter** (no LLM, no new route, no new dispatcher, no new mode). The button/pre-fill is the UI's job; **no chat UI** is built here.

6. Never expose or persist secrets/tokens/PII; sanitize errors. **The ack stores only metadata (chunk, diff hash, optional reason, who, when) — never finding bodies, diffs, or provider errors. Reuse the #28F table shape.**
7. Memory/reviewer findings are **advisory**; source code, user instruction, tests, and safety rules win on conflict. **A finding's only power is to require a human glance; the human always overrides by acknowledging.**
8. AI-suggested memory stays pending until a human approves. (Untouched.)
9. Prefer failing safely with a clear, specific error over guessing. **The safe failure here is *fail-open*: any uncertainty about whether a finding is delivered/current resolves to "no gate," never to a block (§0).**

This PR is **moderate-risk**: it is the first path that lets an AI artifact (a reviewer finding) impose a *procedural* precondition on a human approval gate, and it extends the ack pattern to the chunk gate for the first time. Carry an explicit safety-contract check (§15.5). The risk is **not** a commit/scope/Git regression (those paths are untouched) — it is (a) accidentally letting the reviewer block approval (§0), and (b) touching the two approval routes.

# ITEM 15 — reviewer informed-approval soft gate + "steer this" hook

## 15.1 Summary & scope

A delivered **`high` × {`requirement_mismatch`, `security`}** reviewer finding on a chunk requires an explicit human **acknowledgement** — bound to the chunk's current diff hash — before Approve is enabled, **at both the chunk approval gate and the final approval gate**. The acknowledgement is a **precondition only** (the #28F pattern): it never commits, pushes, creates a PR, rejects, or replaces approval, and it is always satisfiable by the human. An **unavailable/failed/stale/absent review, or a review with no current gating finding, imposes no gate** (§0). Each gating finding **on a `completed` chunk (final-gate surface) or a `failed` chunk** offers a one-click **"steer this"** that reuses the existing steer endpoint to turn the finding into a steer turn; at the chunk-approval gate (`awaiting_chunk_approval`) "steer this" is **not** offered, because `steer_chunk` does not dispatch that status (A4).

**Outcomes the design must deliver (the *what* is fixed; the *how* is yours to design and lay out in the design you submit for review):**
- A **pure gating selector**: given a chunk's *current* review (bound to its current diff hash) and the A1 policy set, return the gating findings (`high` × {requirement_mismatch, security}). A stale/missing/non-`completed` review → empty set. No I/O in the pure core; reuse `current_chunk_review_identity` + `get_review_by_checkpoint_hash` (or `get_latest_review` + staleness check) at the edge. **The edge wrapper that feeds the selector MUST catch every exception and treat an indeterminate identity/lookup as "no current review" → empty gating set (the §0 enforcement fail-open). The selector's default/error branch can never return "blocked."**
- A **review-finding ack store** (sibling of `test_validation_ack_store.py`): diff-hash-bound, idempotent, conflict→409, metadata-only, optional reason; panel-level (A3). Pure `evaluate_*` eligibility + a `chunks_requiring_review_ack(run_id)` blocking selector mirroring `chunks_requiring_acknowledgement:311`.
- A **chunk-gate route precondition** (`_require_review_findings_acknowledged(run_id, chunk_number)`) before `approve_chunk_and_commit` (`approve_chunk_route:2506`) — the NEW attach point (A2). Fires uniformly for fresh, recovered (item 13), and refined (item 14) chunk approvals because it sits above the dispatch. **It fails open: if the gating-set computation or ack lookup raises, it raises no 409 and lets Approve through (§0 enforcement).**
- A **final-gate route precondition** (sibling of `_require_test_validation_acknowledged:2740`), called in `approve_final_approval_route` before `_decide_final_gate` (`:2843`), only when a pending final gate exists. **Same fail-open contract as the chunk-gate precondition (§0 enforcement).**
- A **new ack route** (`POST …/chunks/{n}/review/acknowledge`), sibling of `acknowledge_test_validation_route:2762`.
- **Read-model surfacing** (display only): the chunk read response / operator_state shows "ack required" at the chunk gate and the final gate, reusing the existing review overlay (`chunk_review_read_model`) + the `_ack_decision_from_plan:2095` shape. Enforcement stays in the route; the read model only *describes* it.
- **"Steer this"** via the existing steer surface (A4): offered **only** on `completed`/final-gate and `failed` surfaces (where `steer_chunk` dispatches), **never** at the `awaiting_chunk_approval` chunk gate; no new route/dispatcher/mode; at most one pure `finding_to_steer_text` formatter.
- **Policy:** the A1 set single-sourced in `policy.py`, with a named-but-unbuilt per-project opt-in seam.

**Explicitly out of scope (name these in your PR):**
- The phase/narrative read-model and the trivial-task profile + prompt caching (later Phase 4 slices).
- Any **chat UI** or conversation surface beyond the existing steer endpoint + turn persistence.
- **"Steer this" at the chunk-approval gate** (`awaiting_chunk_approval`) — not offered; `steer_chunk` does not dispatch that status (it 422s) and A4 forbids adding a branch for it (Finding A). The gate's affordances there are acknowledge and reject.
- **Per-project policy overrides** for the ack-required set — ship the default constant + a seam; do not build the override machinery (`policy.py:11-14`).
- Any change to `reviewer.py` / `reviewer_models.py` / `chunk_review_store.py` write paths, to `scope_guard`/`patch_applier`/`path_safety`, to the commit/rollback paths, or to the gate machinery in `approval_gate.py`. The ack is a route precondition over *read* state.
- Giving the reviewer any new authority, or making any finding category beyond A1 gate by default.
- Renaming any DB status string, the `PatchFailureType` taxonomy, the review/finding enums, or the verdict taxonomy.

## 15.4 Traps

- **(a) Letting the reviewer block approval.** The §0 invariant. Gate **only** on a *delivered, current* `high`×A1 finding; everything else (missing/unavailable/failed/pending/stale/read-error/**enforcement-selector exception**/non-A1) is fail-open. If your selector's default branch — or an unhandled exception in the precondition's edge I/O — can ever return "blocked," you've inverted §0. Test all **five** §0 cases (a–e), including the enforcement-selector-raises case at both gates.
- **(b) Gating on a stale review.** A review bound to an old diff hash describes a diff that no longer exists. Use `current_chunk_review_identity` and require the review's `reviewed_test_checkpoint_hash` to equal it (the `classify_review_staleness` rule). A stale review never gates; a fresh review at the new hash re-arms.
- **(c) Inventing a second diff-hash scheme.** Reuse `compute_chunk_diff_hash` for both the review identity and the ack binding (`chunk_review_store.py:13-15` and `reviewer_models.py:15-20` both insist on this). Two schemes = review staleness and ack staleness can diverge = a silently un-acknowledgeable gate.
- **(d) Persisting finding bodies / diffs / provider errors in the ack.** Metadata only (chunk, diff hash, who, when, optional reason), mirroring `test_validation_acknowledgements`. Contract §2.6.
- **(e) Building per-project overrides now.** A1 is a single policy constant this slice; the per-project opt-in is a named seam, default off, **unbuilt** (`policy.py:11-14`).
- **(f) Adding steering backend semantics for "steer this".** A4 forbids it. Reuse `POST …/steer` + `steer_chunk`; at most a pure formatter. No new route, mode, dispatcher, or LLM call. **In particular, do NOT add an `awaiting_chunk_approval` branch to `steer_chunk` to make "steer this" work at the chunk gate — that is new dispatch semantics (Finding A). Mixing them risks a UI that blocks (denial vector) or a route that doesn't. **Because they are separate paths, each must fail open on its own (§0): a test that the *display* overlay fails open does NOT prove the *enforcement* precondition does — cover both (§15.3 (d) and (e)).**
- **(i) A bypassable chunk-gate precondition.** Confirm `approve_chunk_route` is the only human entry to `approve_chunk_and_commit`; if not, attach the precondition where the human approval actually decides, inside the lock.

## 15.5 Safety-contract check (item 15)

- **§2.1 (approved plan / never bypass a gate):** the ack adds a *precondition* to existing chunk and final gates; it creates/replaces/skips none. Prove both gates still fire and the human still makes every approval decision.
- **§2.2 (scope):** "steer this" (offered only on `completed`/`failed` surfaces — A4/Finding A) routes through the unchanged steer path; §5.3 + `scope_guard` still enforce. Prove an out-of-scope "steer this" cannot write.
- **§2.4 (PR/merge):** the gate sits *before* final approval; push/PR still require `FINAL_APPROVED`; no auto-merge. Untouched.
- **§2.6/§2.7 (no secrets/PII; advisory-only):** the ack stores metadata only; findings stay in `chunk_reviews`; the reviewer remains advisory — its only effect is a required human glance, always overridable by acknowledging.
- **§2.9 (fail safe) + §0:** every uncertain path (no/unavailable/failed/stale review, display read error, **enforcement-selector exception**, indeterminate diff identity) fails **open** to "no gate," never to a block — in the **enforcement** precondition as well as the display overlay. The only blocking path is a delivered current `high`×A1 finding, and that block is always cleared by a human ack. **If you cannot prove — at both the chunk gate and the final gate — that a down/absent reviewer and a raising enforcement selector each leave Approve working, stop and escalate.**
